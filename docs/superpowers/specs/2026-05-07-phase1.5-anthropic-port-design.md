## Goal

Replace the 4 stub chain Lambdas in the deployed `casa-coqui-reply-agent` SAM stack with real Anthropic API logic, ported from `functions/lib/reply-agent-chain.js`. After this phase, the deployed SFN can produce a real reply draft when invoked with a realistic synthetic input — but no production traffic flows through it yet (Phase 3 wires the bridge).

## Non-goals

- LoadConfig real implementation (Phase 2 owns this)
- RAGRetrieve real vector search (Phase 2 owns this)
- WriteBack real Firestore writes (Phase 3 owns this)
- Cloud Function bridge from `onAirbnbMessageCreated` to `StartExecution` (Phase 3)
- Deletion of `functions/lib/reply-agent-chain.js` (Phase 3 cleanup)
- AppConfig integration (Phase 2)
- DLQ, SNS alarms, auto-rollback (Phase 3)
- Any change to ASL state machine definitions (existing Retry blocks already declare `AnthropicThrottle`)

## Scope

The 4 chain Lambdas in `infra/sam/reply-agent/functions/`:

- `reasoner/` — generates `response_strategy` via REASONER_TOOL
- `drafter/` — writes the reply via DRAFTER_TOOL
- `evaluator/` — scores the draft via EVALUATOR_TOOL (may produce inline `revisedReply`)
- `reviser/` — re-drafts on evaluator feedback via DRAFTER_TOOL

The 3 stubs that stay as stubs (LoadConfig, RAGRetrieve, WriteBack) remain unchanged.

## Architecture

### Input contract (fat input)

Each chain Lambda receives the full per-message context inline in the SFN execution input. The caller (Phase 3 bridge) is responsible for building this bundle from Firestore.

```jsonc
{
  "message": {
    "id": "abc123",
    "body": "Hi Julio, what time is checkout?",
    "guestName": "Maria",
    "bookingId": "...",
    "threadKey": "..."
  },
  "contextJson":           "<JSON string: thread + booking + settings + voiceSamples + RAG matches>",
  "voicePrompt":           "<reply-ai.js SYSTEM_PROMPT>",
  "voiceProfilePrompt":    "<learned style rules from settings/voice_profile>",
  "relevantConversations": [ { "guestMessage": "...", "hostReply": "...", "distance": 0.12 }, ... ]
}
```

Per-Lambda input requirements:
- `reasoner` → reads `$.contextJson`
- `drafter` → reads `$.contextJson`, `$.voicePrompt`, `$.voiceProfilePrompt`, plus `$.reasoner.strategy` (set by ASL ResultPath)
- `evaluator` → reads `$.drafter.draft`, `$.relevantConversations`, `$.message`, `$.voiceProfilePrompt`, plus `$.reasoner.strategy`
- `reviser` → reads `$.drafter.draft`, `$.evaluator.evaluation`, `$.contextJson`, `$.voicePrompt`, `$.voiceProfilePrompt`, `$.reasoner.strategy`

### Output contract

Each Lambda returns the shape the existing ASL `ResultSelector` expects:

| Lambda    | Return                                                        |
|-----------|---------------------------------------------------------------|
| Reasoner  | `{ strategy: {...}, tokens: { input, output } }`              |
| Drafter   | `{ draft: { reply, language, shouldEscalate, escalateReason? }, tokens }` |
| Evaluator | `{ evaluation: { passed, hardRuleFailures, voiceScore, voiceFeedback, ragConsistent, ragFeedback, propertyFactViolations, revisedReply? }, tokens }` |
| Reviser   | `{ draft: { reply, language, shouldEscalate, escalateReason? }, tokens }` |

### Per-Lambda code organization (decision: Option A — inline)

Three independent staff-engineer reviews unanimously rejected the Lambda Layer approach. Reasons captured below in Decision Log.

```
infra/sam/reply-agent/functions/{reasoner,drafter,evaluator,reviser}/
  package.json    {
                    dependencies: {
                      "@anthropic-ai/sdk":              "^0.x",  // pinned to functions/package.json version
                      "@aws-sdk/client-secrets-manager": "^3.x"
                    }
                  }
  index.js        ~150-200 lines:
                    - module-level cached SecretsManagerClient
                    - module-level cached SECRET VALUE (not just client)
                    - module-level cached Anthropic client
                    - inline copy of throttle wrapper (see below)
                    - inline prompt + tool schema
                    - exports.handler
```

No Lambda Layer. No `_shared/` package. No `file:` deps. Each Lambda is a self-contained unit, opens-one-file-debug.

### Throttle wrapper (the load-bearing piece)

Each Lambda inlines a copy of `functions/lib/anthropic-with-backoff.js` with **one modification**: when retry budget is exhausted on a throttle error, re-throw with `name='AnthropicThrottle'` so the SFN ASL `Retry` block matches it specifically.

```js
// CRITICAL: this name string is a contract with the ASL Retry block.
// Changing it without updating ai-chain.asl.json silently breaks all retries.
const THROTTLE_ERROR_NAME = 'AnthropicThrottle';

async function callWithBackoff(client, params, opts = {}) {
  // ... identical to functions/lib/anthropic-with-backoff.js ...
  // EXCEPT in the exhaustion branch:
  if (attempt + 1 >= MAX_ATTEMPTS && isRetryable(lastErr)) {
    const throttleErr = new Error(lastErr.message);
    throttleErr.name = THROTTLE_ERROR_NAME;     // <-- SFN matches on err.name
    throttleErr.cause = lastErr;
    throw throttleErr;
  }
}
```

**Why per-Lambda backoff PLUS SFN Retry?** Belt-and-suspenders. The Lambda backoff handles the common case (cheap, in-memory retries within 30s). SFN's ASL Retry handles the rare case where the Lambda exhausts its budget and re-throws with the named error — SFN re-invokes the Lambda from cold (a "harder" retry) up to 5 more times with FULL jitter. Total max retries before failing the chain: ~25.

## Verification

### One unit test (the only one)

`infra/sam/reply-agent/functions/reasoner/__tests__/throttle-name.test.js`:

```js
// 5-line test: asserts the throttle error name is exactly 'AnthropicThrottle'.
// Why this exists: a typo here ('AntropicThrottle') silently disables every
// SFN ASL Retry block — SFN won't match, falls to States.TaskFailed (which
// also matches), so it APPEARS to work until a real 429 hits and the wrong
// backoff curve runs. This test is cheap insurance against a string typo.
const { callWithBackoff } = require('../index');  // export from handler module
test('exhausted throttle re-throws with name="AnthropicThrottle"', async () => {
  const fakeClient = { messages: { create: async () => { const e = new Error('rate'); e.status = 429; throw e; } } };
  await expect(callWithBackoff(fakeClient, {}, { sleepFn: () => {} })).rejects.toMatchObject({ name: 'AnthropicThrottle' });
});
```

**Only the Reasoner copy gets the test.** The other 3 Lambdas are byte-identical copies of the same wrapper — verified at copy time via:
```bash
diff functions/reasoner/index.js functions/drafter/index.js | head -40
# (only prompts/tools/handler differ; the wrapper section is identical)
```

New file: `infra/sam/reply-agent/samples/full-input.json` — captured from a real production message (sanitized: guest name + body anonymized, but real `contextJson` / `voicePrompt` / `voiceProfilePrompt` / `relevantConversations` shapes preserved).

#!/usr/bin/env bash
SM_ARN="arn:aws:states:us-east-1:524140443248:stateMachine:casa-coqui-reply-draft"
EXEC_ARN=$(aws stepfunctions start-execution \
  --state-machine-arn "$SM_ARN" \
  --input "file://$(dirname "$0")/../samples/full-input.json" \
  --query executionArn --output text)

while true; do
  STATUS=$(aws stepfunctions describe-execution --execution-arn "$EXEC_ARN" --query status --output text)
  [ "$STATUS" != "RUNNING" ] && break

  --query '{Status:status,StartDate:startDate,StopDate:stopDate,Output:output}' --output json

## Risks & mitigations

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Prompt/tool divergence between JS chain (still serving production) and SAM Lambdas | High during Phase 1.5 → Phase 3 window (days/weeks) | Each Lambda has a comment block referencing the source file + line in `functions/lib/reply-agent-chain.js`. Phase 3 deletes the JS path within ~1 week of Phase 1.5 ship. |
| Cold-start Secrets Manager fetch adds 200-400ms × 4 sequential Lambdas = up to 1.6s | Medium (only on cold chain) | Module-cache the SECRET VALUE (not just the client). At 10 msg/day production volume, sustained warm reuse is unlikely; this is acceptable. Phase 4+ could add provisioned concurrency. |
| Throttle wrapper typo in error name silently breaks all Retry blocks | Low | The `throttle-name.test.js` unit test catches this. |
| Per-Lambda copy of throttle wrapper drifts (one Lambda gets a bug fix, others don't) | Medium over 6+ months | Phase 3 cleanup may consolidate. For now: comment in each copy says `// SOURCE: functions/lib/anthropic-with-backoff.js — sync manually`. Mitigation acceptable given short Phase 1.5 → Phase 3 window. |
| @anthropic-ai/sdk bumps in `functions/package.json` not reflected in Lambda package.json | Low | Pin the same version in all 5 places (functions/ + 4 Lambdas). Add a comment pointing at `functions/package.json` as source of truth. |
| `sam build` time grows from ~10s (stubs) to ~60-90s (4 functions × npm install of large SDKs) | Low | Acceptable. Manual deploy is infrequent. |

## Decision log

### Decision 1: Fat SFN input (caller pre-builds context)

**Picked over:** Thin input + LoadConfig/RAG do real Firestore work in Phase 1.5

**Why:**
- Smallest scope for Phase 1.5
- Mirrors the in-process pattern of `functions/lib/reply-agent-chain.js`
- LoadConfig and RAGRetrieve are explicitly Phase 2 work per `casa-coqui-sfn-refactor-plan.md`
- Phase 3 bridge (Cloud Function → StartExecution) keeps Firestore lookups in the trigger code, where they already live

### Decision 2: Inline per-Lambda (no Lambda Layer)

**Picked over:** Lambda Layer with shared helper

**Why:** Three independent staff-engineer reviews unanimously chose inline. Synthesized reasoning:

1. **Phase 2 will rewrite the abstraction target.** AppConfig + Lambda Extension sidecar (Phase 2, ~2h, next on the queue) replaces both Secrets Manager fetch and prompt-loading patterns. Building a layer now means building it twice — v1 has a 48-72h lifespan.

2. **Rule of three.** 4 copies stamped at the same moment for the same reason isn't 3 real uses — it's 1 use cloned. Real divergence (different retry budget per step? different model per step? thinking-mode on Reasoner only?) hasn't occurred yet. Inline keeps each Lambda free to drift without untangling a layer.

3. **Layer adds operational tax for ~25 LOC of stable boilerplate.** Layer ARN propagation, immutable versioning, "rollback" actually being forward-fix, an extra `sam build` artifact. None of it earns its keep at 10 msg/day with 1 maintainer.

4. **Lambda's 5-layer cap matters.** Phase 2's AppConfig Extension is itself a layer. AWS Powertools (already implied by `POWERTOOLS_*` env vars in template Globals) is another. Adding a custom layer puts us at 3/5 before solving a real problem.

5. **Blast radius is per-Lambda with inline; layer-wide with Layer.** A bug in the throttle-name translator deployed via Layer takes out all 4 retry paths simultaneously. With inline, ship Reasoner first, watch one execution in CloudWatch, then propagate.

6. **"100 lines duplicated" was misleading framing.** That boilerplate is boring, stable, grep-friendly. The real cognitive load is the ~150 lines of unique prompt/tool per Lambda — which a layer doesn't help.

### Decision 3: SDKs in each Lambda's package.json (not in a layer)

**Why:** No layer = no place to bundle SDKs anyway. Each Lambda becomes self-contained.

### Decision 4: One unit test (throttle-name), not a full suite

**Why:** The only NEW logic in Phase 1.5 is the error-name translation. Prompts and tool schemas are byte-copied from a working production module (`reply-agent-chain.js`) — already validated by production traffic. Skipping a full unit test suite is acceptable; one defensive test on the load-bearing string is not skippable per staff engineer #3.

### Decision 5: Module-cache the SECRET VALUE, not just the client

**Why:** Staff engineer #3 caught this. 3 sequential cold starts (Reasoner → Drafter → Evaluator) × 200-400ms each = up to 1.2s of Secrets Manager latency stacked into the chain. Caching the secret value (not just the SDK client) ensures cold-start cost is paid once per Lambda, not once per chain invocation.

### Decision 6: Read MODEL from env var, not from $.config

**Why:** Defaults preserved. LoadConfig stays as stub returning hardcoded model; chain Lambdas read `process.env.MODEL_NAME`. Phase 2's AppConfig refactor changes both at once. No need to wire the pipe early.

### Decision 7: max_tokens hardcoded per-Lambda

**Why:** Matches `reply-agent-chain.js` exactly (1024 for reasoner/evaluator, 512 for drafter/reviser). Phase 2 may externalize if needed.
